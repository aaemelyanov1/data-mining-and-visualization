# Обоснование эскиза «Обзор алертов SOC»

Страница к `sketch/1_eskiz_obzora_alertov.png` (генерируется `sketch/make_sketch.py`).
Все числа проверены по `data/iavd_incidents_raw_target.parquet` — сверка выполняется
автоматически при каждой генерации эскиза.

## 1. Какие три вопроса должен закрывать эскиз

Эскиз — не дашборд, а проверка гипотезы «сработает ли компоновка». Поэтому в нём
три обязательных блока:

| Вопрос | Где на эскизе |
|---|---|
| Что должно выделяться **без чтения подписей** (преаттентивно)? | панель C |
| Как элементы **сгруппированы**? | рамки панелей A–D |
| Чем **закодирован Вердикт**? | панель B, столбцы «FP / не-FP / доля FP» |

## 2. Выбранные поля

| Поле | Роль в эскизе | Почему выбрано |
|---|---|---|
| `Критичность` | измерение (строки матрицы) | единственное поле, которое одновременно задаёт **порядковую шкалу** и делит поток на операционно разные классы |
| `Вердикт` | измерение (столбцы матрицы) | 7 значений; ключевое для качества работы SOC. Вопрос 2.1 банка: `False Positive` 150 675, `Не указан` 54 870, `Решён` 28 606, `Дубликат` 5 819, `Не решён` 316 + 2 редких |
| `Количество инцидентов` | длина полосы в панели A | единственное поле, где важна **интенсивность потока**, а не качество |
| `Создан` (час) | высота столбца в панели D | показывает ритм нагрузки; вопрос 4.4: пик 8:00 (19 118), минимум 0:00 (3 591) |
| `Эскалировался на L2?` | подпись KPI | объём реально эскалированной работы: 1 756 карточек |

`Фаза реагирования`, `Статус`, `Источник` намеренно не вынесены на первый экран:
они объясняют **как** обрабатывается поток, но не помогают решить, куда смотреть
в первую очередь. Для них место во втором клике.

## 3. Обоснование кодировок

Иерархия точности считывания (Кливленд и Макгилл, 1984, лекция 1.1):
**позиция на общей шкале → длина → угол и наклон → площадь → интенсивность цвета.**

| Элемент | Кодировка | Место в иерархии | Почему так |
|---|---|---|---|
| Объём по критичности | длина полосы на общей шкале | 2 | полосы сравнимы между собой; цветом этот факт передаётся хуже всего |
| `Критичность` | **позиция строки** | 1 | шкала порядковая — её место по оси, а не оттенок. Пять оттенков серого различимы плохо и зависят от монитора |
| `Вердикт` | позиция в ячейке + приглушение | 1 / 5 | бинарная свёртка 7 значений в 2 класса — это и есть операционное решение аналитика |
| Доля FP | длина/подпись, **не** цвет | — | доля в процентах читается точно; «красная ячейка» читалась бы только эмоционально |
| Час суток | высота столбца от нуля | 2 | нулевая база обязательна, иначе разница между 3 591 и 19 118 не видна |

**Ошибка, которую эскиз специально показывает:** color-only кодирование «красный/зелёный».
Примерно 8 % мужчин не различают красный и зелёный, а SOC-инструмент — рабочий
инструмент. Цвет здесь несёт роль «плохо / хорошо», но никогда не единственную.

## 4. Преаттентивная цель

Единственный элемент, который обязан находиться без чтения подписей:

```
Критическая + не-FP = 3 060 карточек, чистота 75,0 %
```

Это ~1,3 % потока — ровно та доля, которую стоит разбирать вручную. Остальное
распределение (средняя критичность — 71,2 % FP) показывает, где **не** тратить время.

Парадокс из вопроса 5.9 подтверждён данными: чем выше критичность, тем чаще
алерт настоящий — `Критическая` 25,0 % FP против `Средней` 71,2 %. Значит,
тревога об общем объёме FP обманчива: ложные сидят в массовых классах.

## 5. Группировка (законы гештальта)

- **Близость** — карточки одного узла стоят рядом.
- **Сходство** — одинаковый вердикт даёт одинаковый вид ячейки.
- **Общая область (общий регион)** — каждая панель замкнута рамкой; рамка и есть
  «это один вопрос».
- **Приглушение вместо перечёркивания.** «Неактивное» не выбрасывается из
  сравнения, а приглушается. Полосы остаются на общей оси, поэтому относительные
  размеры читаются.

## 6. Чего в эскизе нет и почему

| Нет | Причина |
|---|---|
| Оттенков «красный/зелёный» как единственного сигнала | ~8 % мужчин не различают; рабочий инструмент |
| 3D, датчиков, перспективы | искажают длину и угол — ломают 2-й и 3-й уровни иерархии |
| Сетки и десятичных подписей осей | поля считываются точнее, чем привязанная к оси величина |
| Отдельного «светофара» по критичности | пять оттенков для порядковой шкалы; заменено позицией строки |
| Значений `Вердикт` кроме FP / не-FP | 7 классов в одной ячейке не читаются; остальные 5 — на детализацию по клику |

## 7. Проверяемость

`sketch/make_sketch.py` при каждом запуске сверяет часовые значения с parquet и
печатает `часовые значения сверены с parquet: совпадают`. Растровая вёрстка
дополнительно проверяется на выход текста за полотно и наложения подписей.

Числа соотнесены с банком вопросов: 2.1 (`Вердикт`), 4.4 (час пика/минимума),
5.9 (доля FP по критичности), 5.10 (доля FP по линиям), 6.7 (эскалация на L2).

## 8. Открытый вопрос

**4.3 в `ml/1.5_eda_soc_incidents.py`:** строгий календарный фильтр полных месяцев
даёт максимум `2024-05 = 4 576`, а ключ ответа — `2025-07 = 5 216`. Это
непротиворечиво только при дополнительном исключении периода развёртывания SOC
(апрель–май 2024). Скрипт печатает оба варианта; какой из них защищать перед
комиссией — нужно уточнить у преподавателя.
